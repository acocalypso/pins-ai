## Data integrity and supervision

Original package files and their hashes remain preserved. Audited copies are in
`training/datasets/mcp-v2/data/audited`: 924 train, 583 validation, 593 test
conversations. Tool declarations are replaced by source-generated definitions;

The stop-guiding job kind/resource and nullable job fields are corrected.
Updated fixtures repair 164 status responses to contain all eleven simulated
device slots with null names for disconnected devices. They also repair 39
start-sequence and 38 stop-sequence replies across the three splits: sequence
running is not imaging completion; a stop request needs actual status verification,
not `get_job` polling when no job identifier was returned.

Gold sets are unchanged: 593 eval_gold and 120 hard_gold cases. Test/gold are
never exported for training. Original schema validation passed; the stronger
checks validate all original hashes, audited arguments and scenario separation.
Training re-renders every train/validation assistant turn from the audited source
and compares token IDs and labels before accepting prepared files.

The actual pinned local Qwen tokenizer yields 1,908 train and 1,236 validation
assistant turns across all ten languages and 32 tools, with **zero skipped**
turns. Revised training lengths: median 620, p95 993, max 1,245 tokens; validation median
639, p95 984, max 1,236. A 1,280-token budget retains every turn. Tool property
descriptions are omitted from prompts to save space, but schema types, units in
the system policy, names, required fields, enums and ranges remain enforced.

Each assistant turn is a separate prompt/completion example. The real tokenizer
renders `<tool_call>` JSON and `<|im_end|>`; every system/user/previous-assistant/
tool token is masked. Only the current assistant completion and end marker
contribute to loss. Prefix/token-boundary mismatches and overlong samples fail
loudly. No raw JSONL text training or silent token-limit filtering occurs.

These are synthetic fixtures and translated template families, not independent
live sessions or proof of native fluency. Native review and independent team
requests remain necessary. Some original hard-gold labels for connect/emergency
stop express an intended tool without out-of-band approval. Intent scoring must
not turn those labels into execution permission; the gateway still requires it.

## Plugin integration boundary

`McpClient.cs` and `ToolGateway.cs` are compiled into the existing dependency-light
plugin runtime library. They add an actual MCP client and an enforceable gateway:
known-tool allowlist; type/schema/range/cross-field checks; no force,
skip_validation or overwrite; fresh rig state; active-sequence protection;
live switch limits; confirmations bound to exact parameters, rig/chat, request
ID and expiry; single-use approvals; cancellation and bounded job polling.
Omitted `wait_seconds` becomes zero before preview/confirmation, avoiding the
server's 30-second default; the approval covers the effective arguments sent.
Unknown/unexposed tools cannot execute. Read-only annotations changing on a
known query require a new audit. tools/call is internal to the runtime and enters
through the gateway. Mutating call failures are never automatically retried.

The client handles initialization, notification, negotiated protocol, session
headers, tools/list, bounded tools/call results and session deletion. Failed jobs
inside isError:false envelopes remain unsuccessful. Running jobs are polled with
get_job, at most eight times within a 30-second deadline. Tool `next` text cannot
create an approval or execute another operation.

**The current chat API does not yet enable MCP generation/execution.** These
components are tested building blocks; the existing ChatPolicy still says tools
are unavailable. Before exposing v2 chat, the plugin must own the client/gateway
through Initialize/Teardown, create server-derived rig context and isolated chat
state, pass actual selected tools to inference using the matching Qwen template,
and connect authenticated operator preview/confirm handlers. Model/tool output
must never reach the confirmation handler. Hardware remains unavailable until
those bindings and the existing server's host wiring are verified.

The existing plugin-owned, supervised loopback llama.cpp child remains the model
owner's inference implementation, with cancellation, shutdown/parent-death and
memory/thermal guards. No new daemon/systemd service or UI was added. Emergency
operator controls remain independent of inference and its confirmation flow.
